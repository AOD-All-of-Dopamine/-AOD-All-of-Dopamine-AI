# 계획 — 평가 기반을 LLM 채점에서 **행동 데이터**로 옮긴다 (2026-09-04)

## 결론 먼저

**랭커를 더 손대기 전에 잣대를 고친다.** 지금 병목은 추천 품질이 아니라 **그것을 잴 수단**이다.

병렬로 웹툰을 마무리하고, 오늘 **랭킹 스냅샷 수집을 시작한다**(안 하면 시간 축이 영영 안 생긴다).

---

## 1. 왜 잣대인가 — 최근 4개 실험이 전부 같은 곳을 가리킨다

| 실험 | 발견 | 뜻 |
|---|---|---|
| X-22 | 채점 프롬프트를 바꾸니 `quality_w` 판정이 뒤집혔다 | **잣대가 답을 정한다** |
| X-24 | 근거 있는 페르소나 0.662 vs 내가 지어낸 페르소나 0.909 | **val 집합이 검증 안 됨** |
| X-25 | 중복 시드 3개(0.906)가 다양한 3개(0.834)를 이긴다 | **지표가 다양성을 벌준다** |
| 2차 검수 | 보정 지배도 Steam 84% · TMDB 72% | **우리가 튜닝한 건 필터에 가깝다** |

넷을 합치면 이렇게 된다 — **축을 하나 더 판정해도 그게 개선인지 잣대의 성질인지 구분할 수 없다.**
D-32 동어반복이 4개월째 안 풀리는 것도 같은 이유다: 고치면 P@50이 떨어지게 **설계된** 지표다.

이 상태에서 랭커 실험을 더 쌓으면 **오차가 누적된다.**

## 2. 탈출구가 생겼다 — 진짜 행동 데이터

2026-09-04 실측으로 **두 경로가 열려 있음을 확인했다**:

```
Steam 리뷰 API  → steamid + 플레이타임          (게임당 100건씩, 키 불필요)
  → GetOwnedGames → 유저별 보유 게임 + 게임별 플레이타임   (우리 키로 동작, 표본 2/2 공개)
TMDB /recommendations → 아이템-아이템 CF 출력    (인셉션 → 20편 정상)
```

**이게 X-23의 각색 쌍보다 강하다.** 각색 쌍은 "개체 연결"까지만 답했다(같은 이야기를 매체 건너 잇는가).
공동보유는 **취향 자체**의 데이터다 — "이 게임을 하는 사람이 저 게임도 한다".

없는 것: 네이버(웹툰·웹소설)는 개인 단위 공개 데이터가 없다. 여기는 콜드스타트가 남는다.

## 3. 반드시 조심할 것 (설계에 먼저 박는다)

행동 데이터를 잘못 쓰면 **인기 재발명**으로 끝난다. 우리가 이미 앓는 병이다.

1. **원시 공동보유는 인기에 지배된다.** 무엇과든 같이 팔리는 것이 1등이 된다.
   → **PMI 등 정규화**를 쓴다. 원시 카운트를 정답으로 쓰지 않는다.
2. **보유 ≠ 좋아함.** 번들·세일로 산 미실행 게임이 많다.
   → **플레이타임 하한**을 건다. 하한값은 사전등록에서 관측 전에 고정한다.
3. **리뷰어는 일반 유저가 아니다.** 적극적인 층에 치우친다.
   → 결과에 이 편향을 명시한다. "일반 사용자"로 일반화하지 않는다.
4. **취향 폭 ≠ 추천 적합.** 위쳐와 스타듀를 다 가진 사람은 취향이 넓은 것이지
   "위쳐 팬에게 스타듀가 좋은 추천"이라는 뜻이 아니다.
   → 판정문에 이 한계를 X-23의 "개체 연결 ≠ 취향" 문장과 같은 자리에 적는다.
5. **랭킹은 정답이 아니라 탐침이다.** 인기 순위를 P@k 문턱에 넣지 않는다.
   X-23에서 인기 top-50은 **대조군(R@50 0.040)** 이었다. 그 자리를 지킨다.

## 4. 단계

### P0 — 랭킹 스냅샷 수집 시작 (오늘, 비용 ~0)
**지금 시작 안 하면 시간 축이 영영 안 생긴다.** 현재 우리한테 시계열이 하나도 없다:

| | 시간 축 |
|---|---|
| Steam | `release_date`(한글 문자열) · CCU 스냅샷 1회 · `steam_rank` 96편뿐 |
| TMDB | `date`(개봉일) 결측 0 — 유일하게 쓸 만함 |
| 웹소설·웹툰 | **없음** |

할 일: 네 플랫폼 인기순을 하루 한 번 jsonl 에 append 하는 수집기.
쓰는 곳은 **판정이 아니라 진단** — 코퍼스 신선도 · 인기작 도달 순위 · 출시연도 편향.

### P1 — Steam 공동보유 파일럿 (반나절)
게임 20개로 재서 **본 수집 규모를 추정**한다. 재는 것:
- 리뷰에서 얻는 고유 steamid 수 / 게임
- **공개 프로필 비율** (표본 2개로는 모른다)
- 유저당 보유 게임 수 분포 · 플레이타임 분포
- 레이트 리밋에서의 실제 처리량

파일럿 결과로 본 수집이 **몇 시간짜리인지 며칠짜리인지** 정한다.

### P2 — 본 수집 + 정답 집합 구축
목표: 유저 수만 명 × 보유/플레이타임. 여기서 **아이템-아이템 정답**을 만든다
(PMI 정규화 · 플레이타임 하한 적용). 우리 코퍼스 173,691편 중 실제로 덮이는 범위도 같이 잰다.

### P3 — 사전등록 판정: 현행 Steam 추천 vs 행동 정답 (**LLM 채점 없음**)
X-23과 같은 형식. 시드 → 현행 top-50 이 **행동 상위**를 얼마나 잡는가.
관측 전에 문턱을 봉인한다. 여기서 갈리는 것:

- 잘 잡으면 → 우리 LLM 잣대가 대체로 옳았다는 **독립 확증**. 랭커 실험을 계속한다.
- 못 잡으면 → **지금까지의 확정값이 행동과 어긋난다.** 그 경우 D-38(`quality_w`)·D-49(`tag_w`) 같은
  큰 축부터 행동 정답으로 재판정한다.

**어느 쪽이든 이번엔 값을 바꾸지 않는다.** 판정만 한다.

### P4 (병렬) — 웹툰 마무리
행동 데이터가 없으니 **기존 방식(LLM 채점)으로** 간다. 대신 P3 결과가 나오면
그 보정을 웹툰 숫자에 소급해 적는다.
1. `rep_v1` vs `rep_v2` 사전등록 판정 ← **첫 축**
2. 이긴 표현으로 기준선 → `pop_boost` → `tag_w` → `strategy` → `hub_lambda` → `star_boost`

### P5 — TMDB `/recommendations` 로 반복
같은 논리를 TMDB에. 남의 CF 출력이라 수집이 훨씬 싸다(59,780편 조회).

---

## 5. 왜 이 순서인가

**P3 를 P4 보다 먼저 두고 싶었지만 그러지 않았다.** 웹툰은 이미 절반 지어졌고
방치하면 낭비다. 채점은 병렬로 돌릴 수 있어 벽시계 비용이 거의 안 든다.

**P0 를 맨 앞에 둔 이유**는 비용이 0인데 **오늘 시작해야만** 한 달 뒤에 쓸 수 있어서다.
나머지 순서는 전부 뒤집을 수 있지만 이건 못 뒤집는다.

**P1 파일럿을 P2 앞에 둔 이유**는 공개 프로필 비율을 모르기 때문이다.
표본 2개로 100%를 봤지만 그건 아무 의미 없는 표본이다. 30%면 계획이 달라진다.

---

## 6. 하지 않을 것

- **인기 랭킹을 P@k 문턱에 넣지 않는다.** 탐침으로만 쓴다.
- **행동 데이터로 값을 즉시 바꾸지 않는다.** P3 는 판정만 한다.
- **네이버 개인 데이터를 긁지 않는다.** 공개돼 있지 않다.
- **웹툰을 P3 결과까지 기다리게 하지 않는다.** 병렬로 간다.
- **잣대를 조용히 바꾸지 않는다.** X-22 에서 프롬프트를 바꿔 라운드 비교를 망친 적이 있다.
  잣대 변경은 **별도 사전등록**으로만.

## 7. 성공 기준

| 단계 | 끝났다고 말할 수 있는 조건 |
|---|---|
| P0 | 네 플랫폼 랭킹이 매일 jsonl 에 쌓인다 |
| P1 | 공개 프로필 비율·처리량 실측 → 본 수집 시간 추정치 |
| P2 | 유저×아이템 행렬 + PMI 정답 집합, 코퍼스 피복률 기록 |
| P3 | **LLM 채점 0건**으로 낸 판정문 + 사전등록 md5 |
| P4 | 웹툰 확정값 최소 3개 (표현 · pop_boost · tag_w) |
| P5 | TMDB 행동 정답 판정문 |
