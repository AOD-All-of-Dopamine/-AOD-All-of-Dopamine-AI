# 유튜브 · 당근은 추천 시스템을 어떻게 만들었나 — 그리고 우리와 무엇이 다른가

작성 2026-09-15. 1차 자료(논문 원문, 공식 기술 블로그, 채용 블로그, AWS 공동 기고, 고객센터 FAQ)를 기준으로 정리했다.
원문으로 확인하지 못한 내용은 **[미검증]** 으로 표시했다. 출처는 문서 끝에 모았다.

## 0. 한눈에

| | 유튜브 | 당근 | 우리 (AOD) |
|---|---|---|---|
| 출발점 | 함께 시청된 영상(co-visitation) + 규칙 랭킹 (2010) | 최신순 피드 + 서비스별 고정 슬롯 → 딥러닝 2단계 (2019) | 작품 텍스트 임베딩 유사도 + 규칙 보정 |
| 핵심 신호 | 시청 행동(암묵) → 시청 시간 → 만족(설문) | 클릭·채팅·관심·숨기기 + **지역·최신성** | 사용자가 고른 좋아요 작품 (행동 로그 없음) |
| 구조 | 후보 생성 → 랭킹 → 다양화 | 후보(지역·최신) → 랭킹 → 피드 믹서 | 플랫폼별 후보·랭킹 → 후처리 → 플랫폼 혼합(M6) |
| 판정 | **실사용자 A/B** | **실사용자 A/B** (월 ~290건) | LLM 3역할 눈가림 채점 (오프라인) |
| 실시간 반영 | 요청마다 최근 행동 반영 | 행동 피처 실시간 적재, 임베딩만 24시간 배치 | 요청마다 좋아요를 넘기므로 즉시 (저장 상태 없음) |

**가장 큰 차이 세 가지**
1. 두 회사는 처음부터 **사용자 행동 로그**가 추천의 재료였다. 우리는 로그가 없어 **작품 내용**만 쓴다.
2. 두 회사는 **실사용자 A/B** 로 판정했고, 오프라인 지표와 온라인 결과가 자주 어긋난다고 반복해서 적었다. 우리 판정은 전부 오프라인 LLM 채점이다.
3. 두 회사는 **무엇을 최적화할지**(시청 시간, 클릭·채팅 전환)를 사업 목표에서 정했다. 우리는 "좋아요와의 관련성"만 본다.

## 1. 유튜브

### 1-1. 2010 — 함께 시청된 영상과 규칙 랭킹 (Davidson 외, RecSys 2010)

**구조**
1. **관련 영상**: 24시간 동안 한 세션에서 두 영상이 함께 시청된 횟수 `c_ij` 를 세고 두 영상의 인기로 나눈다 — `r = c_ij / (c_i · c_j)`.
2. **후보 생성**: 사용자가 시청·좋아요·재생목록에 넣은 영상을 시드로, 관련 영상 그래프를 몇 단계 넓힌다. 각 후보가 **어느 시드에서 왔는지** 기록한다.
3. **랭킹**: 영상 품질(조회·평점·공유·업로드 시각) + 사용자 특화(시드의 시청량·시각)를 선형 결합.
4. **다양화**: 시드 하나당 추천 수 상한 · 같은 채널 추천 수 상한.
5. **서빙**: 요청 시 계산하지 않고 하루 여러 번 **배치로 미리 계산**. 매 방문마다 일부만 보여줘 새로 계산 없이도 달라 보이게 했다.

**생각**
- 목표: 최신이고, 다양하고, **최근 행동과 관련 있고**, 사용자가 **왜 추천됐는지 이해할 수 있는** 추천.
- 제약: 메타데이터가 부실하다 → 내용이 아니라 **행동**을 신호로 썼다. 영상은 며칠 만에 뜨고 진다 → 신선도가 필수.
- 시드와 너무 가까운 것만 주면 "새로운 것"이 없다 → 그래프를 몇 단계 넓혔다.

**평가**: 실서비스 A/B. 클릭률, 끝까지 본 클릭률, 세션 길이, 커버리지. 홈 화면 클릭의 약 60% 가 추천에서 나왔고, 같은 위치 비교에서 추천의 클릭률은 "가장 많이 본 영상" 목록의 207%.

### 1-2. 2012 — 조회수에서 시청 시간으로 (공식 블로그)
"누르고 바로 떠나는" 영상이 조회수 기준에서 올라가는 문제 → 검색·추천을 **시청 시간** 중심으로 바꿨다.
2021 블로그에 따르면 도입 직후 **조회수가 20% 떨어졌지만** 실제로 보는 가치를 우선했다.

### 1-3. 2016 — 딥러닝 2단계 깔때기 (Covington 외, RecSys 2016)

**구조**
1. **후보 생성** (수백만 → 수백): "다음에 볼 영상"을 맞히는 초대형 분류 문제. 입력은 시청 영상 임베딩 평균, 검색어 임베딩 평균, 지역·기기, 인구통계. 서빙은 최근접 벡터 검색.
2. **랭킹** (수백 → 수십): 수백 개 피처. 가장 강한 신호는 **이 사용자가 이 채널·비슷한 영상과 과거에 어떻게 상호작용했는가**. 어떤 후보 소스가 추천했는지, **이미 보여줬는데 안 본 횟수**도 피처로 넣어 다음 요청에서 순위를 내린다.
3. **학습 목표**: 가중 로지스틱 회귀 — 클릭된 노출은 시청 시간으로 가중 → 점수가 곧 기대 시청 시간.

**생각 (저자 서술)**
- **클릭률이 아니라 시청 시간**: 클릭률은 낚시성 영상을 올린다.
- **명시 피드백(좋아요·설문)보다 암묵 피드백(시청)**: 명시 피드백은 너무 희소해 롱테일을 추천할 수 없다.
- **무작위로 뺀 시청이 아니라 "다음 시청"을 맞힌다**: 시청은 순서가 있고(시리즈, 대중→틈새), 무작위 홀드아웃은 미래 정보를 새게 한다.
- **사용자당 학습 예제 수 고정**: 헤비 유저가 모델을 지배하지 않게.
- **추천 경유 시청만이 아니라 모든 시청으로 학습**: 안 그러면 새 콘텐츠가 떠오르지 못하고 이미 추천하던 것만 강화된다.
- **신선도**: 학습 때 "예제 나이"를 피처로 넣고 서빙 때 0 으로 둬, 막 올라온 영상의 인기를 표현하게 했다.

**평가**: 개발 중에는 오프라인 지표, **최종 판단은 A/B** — "라이브 A/B 결과는 오프라인 실험과 항상 상관되지 않는다."

### 1-4. 2019 — 여러 목표, 편향 보정, 장기 만족

### 1-5. 2021 — 공식 설명 (블로그·도움말)
- 신호: 시청 기록, 검색, 구독, 좋아요, **싫어요, "관심 없음", "채널 추천 안 함"**, 만족도 설문.
- **"가치 있는 시청 시간"**: 1~5점 설문에서 4~5점 받은 시청만 센다. 응답 안 한 사람은 설문 응답을 예측하는 모델로 채운다.
- 신호의 중요도는 사람마다 다르다(뭐든 공유하는 사람은 공유 신호 비중을 낮춘다).
- 싫어요·관심 없음은 "앞으로 무엇을 추천하지 말지 알려준다" — **완전 제외인지, 감점인지, 비슷한 영상까지 퍼지는지는 공개되지 않았다 [미검증]**.
- 신규 사용자: 2016 논문은 인구통계 피처가 "새 사용자에게 합리적인 사전값"이라 적었다. 시청 기록이 꺼져 있고 과거 기록도 없으면 홈 추천이 나오지 않는다(도움말).

## 2. 당근

### 2-1. 2019 이전 → 2019 — 최신순 피드에서 딥러닝 2단계로
- **이전**: 최신순 피드 + "몇 번째는 알바, 몇 번째는 ○○" 식 **서비스별 고정 슬롯** (채용 블로그 인터뷰).
- **2019-05 (기술 블로그)**: 유튜브·핀터레스트를 참고한 **2단계 구조**.
  1. 후보 모델: 사용자·게시글 벡터 곱(MF) + 본 글 순서로 다음 글을 맞히는 시퀀스 모델 + FAISS 최근접 검색. 수백만 → 수백.
  2. 랭킹: 사용자·게시글 피처를 이어 붙인 신경망 점수.
  3. 입력: 최근 본 글 50개 · **지역** · 시각. 지역은 조건으로 학습하고, **게시 후 시간이 지날수록 감점**.

**생각**
- **최신성**: "사용자가 보는 글의 70% 가 7.3시간 이내 글." 중고 물건은 금방 팔려 사라진다.
- **확장성**: 기존 협업 필터링은 데이터가 늘자 메모리·학습 시간이 폭증 → 먼저 줄이고 나중에 정밀하게.
- **평가(오프라인)**: MAP 0.12 · Top-50 적중 12%.

### 2-2. 현재 홈 피드 구조 (고객센터 FAQ · Feed Infra 팀 글 2023)
- **후보**: "주로 **동네별 최신 글**" + 머신러닝·통계로 뽑은 글.
- **순서**: "**클릭이나 채팅할 확률**을 예측하는 머신러닝 모델". 반영 요소 = 최신성(새 글·끌어올린 글) · 관심사(조회·관심·채팅 이력) · 게시글 품질.
- **서빙 3요소**:
  - **Feed Mixer** — 개인화 콘텐츠와 **성장 중인 서비스의 콘텐츠를 섞고** 정책 페널티 적용
  - **Feed Entity Service** — 모든 서비스 콘텐츠를 모은 통합 저장소
  - **Implicit Feedback Service** — 관심·좋아요·댓글·채팅·신고 저장
- **2023 스택 (피드품질팀 인터뷰)**: 클릭과 전환을 함께 예측하는 다중 목표 신경망 · CLIP 콘텐츠 임베딩 · GNN 임베딩 · 탐색(exploration) 연구 · 초당 6,000건 이상.
- **다양성**: LLM 으로 분류한 카테고리로 "비슷한 카테고리 글이 연달아 나오지 않게" 하고, 테니스 라켓 → 테니스 모임처럼 서비스 교차 추천에도 쓴다.

### 2-4. 2026 — 지역 제약을 학습에 넣은 장기 사용자 모델 (기술 블로그 · arXiv)
- 사용자 타워: 최근 행동 **1,024개**를 읽는 Transformer · 게시글 타워: **LLM 콘텐츠 임베딩** + MLP. 사용자 임베딩은 24시간마다 갱신.
- 이 임베딩을 홈 피드 후보 · 홈 피드 랭킹 · 광고 랭킹이 **공통 피처**로 쓴다.

**생각**
- **거래의 86% 이상이 반경 5km 안.** 무작위 배치 학습에서는 음성 샘플의 98% 가 사용자가 **애초에 볼 수 없는 지역의 글**이었다 → 같은 지역끼리 배치를 묶어(RCBS) 30% 로 낮췄다.
- **ID 임베딩 대신 콘텐츠 임베딩**: 신규 글 콜드스타트, 그리고 파라미터의 99% 이상을 ID 임베딩 테이블이 차지하던 문제.
- **장기 이력**: 계절 관심사·서비스 교차 관심을 잡고, "모델이 보여준 것만 다시 학습하는" 순환을 피하려고.

**결과**: 오프라인 후보 Recall@10 +7.56% · 랭킹 NDCG@10 +1.18% · 온라인 클릭 +10.0% · 광고 CTR +7.46%.

### 2-5. 동네생활 피드 — ML 인력이 없는 팀의 구조 (기술 블로그 2026)
서버가 사용자·지역으로 후보 목록 → 추천 엔진이 순서 결정 → 노출 범위·정책 적용. 다음 페이지 후보는 캐시.
**추천 엔진이 늦거나 실패하면 후보 목록의 기본 순서로 대체한다.** 커뮤니티실에는 전담 ML 엔지니어가 없다고 밝혔다.

### 2-6. 신호와 실시간 반영 (Feature Store 글 2024 · AWS 기고 2025)
- 신호: 조회·클릭, **채팅**, 관심(찜), 검색 키워드, 키워드 알림, 체크인 지역, 좋아요·댓글·신고, **"이 글 숨기기"**, 구매.
- **실시간**: 클릭한 글·채팅한 글 같은 행동 피처를 사용자별 최근 30~50개로 저장. 요구사항은 "행동 피처와 특성 피처가 **모두 실시간으로** 갱신". 이벤트 큐(Kafka 등) → DynamoDB·Redis. 차단 목록 같은 것은 요청 시점에 계산.
- 인프라: 피처 4개로 시작해 약 70개(2023-12), 피크 약 13만 요청/초. v2 는 3계층 캐시로 10만+ RPS · P99 30ms 미만.
- 숨기기가 모델 감점으로 쓰이는지 필터로만 쓰이는지 — **찾지 못함.** 체류시간 신호 — **[미검증]**.

### 2-7. 평가·실험 문화
- 2022 Firebase A/B 신뢰성 문제로 **자체 실험 플랫폼** 구축. 누적 4,600건, 월 약 290건(2026-08).
- 피드실이 보는 지표: 클릭, 전환, **숨기기 비율 감소**, p99.9 지연, 전사 지표·매출 기여.
- 원칙: "실험은 결정을 대신하지 않는다. 장기적으로 제품 경험을 해치면 실험 결과가 좋아도 반려한다."

## 3. 두 회사의 공통 원칙

1. **먼저 줄이고, 나중에 정밀하게** — 싸고 넓은 후보 생성 → 비싼 랭킹 → 다양화·정책. 둘 다 이 뼈대에서 벗어나지 않았다.
2. **행동이 내용보다 강한 신호** — 유튜브는 메타데이터가 부실해서, 당근은 물건이 금방 사라져서 행동을 택했다. 다만 둘 다 **콜드스타트** 때문에 결국 **콘텐츠 임베딩**을 다시 끌어들였다(유튜브 2019 two-tower, 당근 2026 LLM 임베딩).
3. **무엇을 최적화할지가 설계를 정한다** — 클릭률의 함정(낚시성)을 겪고 시청 시간·전환·만족으로 옮겼다.
4. **판정은 실사용자** — 오프라인 지표와 온라인 결과가 자주 어긋난다고 둘 다 적었다.
5. **자기 추천이 만든 편향을 경계** — 위치 편향, "보여준 것만 다시 학습", rich get richer. 탐색·편향 보정·전체 시청 학습으로 대응.
6. **다양성은 규칙으로** — 시드별·채널별 상한(유튜브), 비슷한 카테고리 연속 금지(당근).
7. **실패해도 피드는 나온다** — 당근 동네생활은 추천 엔진이 실패하면 기본 순서로 대체.

## 4. 우리 시스템 (AOD) 현황

- **재료**: 작품 텍스트를 Qwen3-Embedding-0.6B 로 임베딩(Steam 설명·태그·장르 / TMDB 줄거리·키워드·장르 / 웹툰 제목·장르·태그·줄거리 / 웹소설 제목·장르·줄거리). 다른 사용자의 행동은 전혀 쓰지 않는다.
- **흐름**: 좋아요 작품마다 따로 유사도 → 한 점수로 접기(top2_mean 등) → `유사도 × (1 + 보정)` (태그·장르 겹침, 평점, 품질, 매체 일치) → 후처리(성인물 제외, 시리즈 1편·작가 2편 상한, 시드 속편 제외, 시드별 번갈아 배치) → 플랫폼 혼합 M6.
- **규모·지연**: 코퍼스 3.7천(웹툰) ~ 17만(Steam) · 모델 호출 없음 · 지연 중앙 91~584ms · 메모리 합계 약 4.3GB.
- **반영**: 요청마다 좋아요를 넘기므로 좋아요 변경은 즉시. 싫어요 유사 감점은 Steam 만 있고(미채점), 웹툰 T-11 은 **(C) 기각** — 싫어요 작품·시리즈 제외만 동작.
- **판정**: 사전등록 → md5 봉인 → 3역할 LLM 눈가림 채점 → 문턱 판정. 행동 로그·A/B 없음.

## 5. 무엇이 다른가 — 항목별

### 5-1. 신호: 행동 vs 내용
| | 유튜브·당근 | 우리 |
|---|---|---|
| 재료 | 시청·클릭·채팅·관심·숨기기 로그 | 작품 텍스트 + 사용자가 고른 좋아요 |
| 강점 | "같은 사람들이 함께 좋아한 것" — 장르가 달라도 찾는다 | 로그 없이 첫날부터 동작 · 신규 작품도 바로 추천 |
| 약점 | 콜드스타트 → 결국 콘텐츠 임베딩 도입 | **줄거리·태그가 비슷한 것**만 찾는다. 뜻밖의 발견이 약하다. 메타데이터가 부실하면 못 찾는다 |

유튜브 2010 이 메타데이터 대신 행동을 택한 이유가 정확히 우리의 약점이다. 반대로 두 회사가 콜드스타트 때문에 **나중에** 도입한 콘텐츠 임베딩이 우리의 **출발점**이다 — 순서가 반대다.

### 5-2. 최적화 목표
- 유튜브: 클릭 → 시청 시간 → **만족(설문으로 가치 있는 시청)**. 조회수 20% 하락을 감수했다.
- 당근: **클릭·채팅 전환** 확률, 숨기기 비율 감소, 매출 기여.
- 우리: "좋아요 시드와 관련 있는가" 하나. 사업 지표와 연결돼 있지 않다. 채점자가 시드와 닮은 것에 점수를 더 주는 **메아리 편향**이 알려져 있다(T-11: 빠진 작품 적합 0.78 vs 들어온 작품 0.68).

### 5-3. 랭킹
- 두 회사: 수백 개 피처의 **학습된 모델**, 여러 목표를 함께 예측(유튜브 MMoE, 당근 다중 목표 신경망).
- 우리: **사람이 정한 공식**과 계수. 계수 하나를 바꿀 때마다 사전등록·채점 한 라운드. 학습할 레이블(행동)이 없어서 이 방식이 강제된다.

### 5-4. 싫어요·부정 피드백
- 유튜브: 싫어요·관심 없음·채널 추천 안 함을 받아 "추천하지 말 것"에 쓴다 — **구체적 방식 비공개.** 2019 논문은 dismiss 를 만족 목표의 하나로 학습.
- 당근: "이 글 숨기기"를 받고 **숨기기 비율 감소**를 피드실 지표로 본다 — 모델 반영 방식은 찾지 못함.
- 우리: Steam 만 유사 감점(미채점). 웹툰은 T-11 에서 규칙 감점이 반영 크기를 못 채웠다. **두 회사도 규칙 감점이 아니라 학습 목표·지표로 다룬다**는 점이 차이다.

### 5-5. 실시간 반영
- 당근: 행동 피처를 이벤트 큐로 **실시간** 적재, 무거운 사용자 임베딩만 24시간 배치. 가벼운 것은 즉시, 무거운 것은 배치 — 층을 나눴다.
- 유튜브 2010: 추천은 배치 계산, 매 방문 일부만 노출. 2016: 이미 보여줬는데 안 본 횟수를 피처로 넣어 다음 요청에 반영.
- 우리: 사용자 상태를 저장하지 않고 요청마다 좋아요·이미 본 것을 넘긴다 → 좋아요는 즉시 반영된다. **"보여줬는데 안 누른 것"** 신호는 없다(노출 로그가 없어서).

### 5-6. 평가
- 두 회사: 오프라인 지표는 개발용, **최종 판단은 A/B.** 당근은 월 290건.
- 우리: LLM 3역할 채점이 유일한 판정. 사전등록·봉인·미채점 0 규율은 엄격하지만 **실사용자 반응이 아니다.** 단일 라운드 효과가 재현되지 않은 사례(TMDB V-2→V-3, 웹툰 T-7→T-8)가 이 잣대의 잡음 폭을 보여준다.

### 5-7. 여러 서비스 섞기
- 당근: 서비스별 개인화 → **Feed Mixer 로 전체 최적화**, 성장 서비스 콘텐츠를 의도적으로 섞음, 공통 사용자 임베딩.
- 우리: 플랫폼별 랭커를 따로 두고 **명시적 할당(M6)** 으로 섞는다. 플랫폼 간 공통 임베딩 공간은 두지 않기로 했다(crossdomain/DESIGN.md). 당근의 2023 이전 구조(서비스가 1차 정렬 → 피드가 최종 순서)와 비슷하다.

### 5-8. 인프라·장애 대비
- 당근: 피처 스토어(13만 RPS), 추천 서버 분리(2021), 추천 실패 시 기본 순서.
- 우리: numpy 전량 내적, 백엔드 미연동. 백엔드 통합 설계에서 추천 서비스 분리 + 실패 시 랭킹 대체를 제안한 상태.

## 6. 우리에게 주는 시사점 (제안 — 결정 아님)

1. **노출·클릭 로그를 서빙 첫날부터 켠다.** 두 회사의 모든 발전은 로그 위에서 일어났다. 로그 설계는 `REC_TAB_DESIGN.md` §5(요청·응답·노출·행동 로그, 백엔드 m2 브랜치 뼈대를 대체). 나중에 켜면 그 전 기간 데이터는 영구히 없다.
2. **판정을 점진적으로 실사용자로 옮긴다.** 로그가 쌓이면 LLM 채점은 "출시 전 안전 검사"로 역할을 줄이고, 클릭률·좋아요율·숨기기율로 판정한다.
3. **최적화 목표를 정한다.** 클릭? 좋아요? 상세 페이지 체류? 유튜브가 클릭률의 함정을 겪었듯, 목표가 정해져야 랭킹 계수의 방향이 정해진다.
4. **"보여줬는데 안 누름"을 신호로 쓴다.** 유튜브 2016 의 노출 빈도 피처와 같은 발상 — 노출 로그가 생기면 가장 싸게 얻는 부정 신호다.
5. **싫어요는 규칙 감점보다 지표로 먼저 본다.** 당근처럼 "숨기기/싫어요 비율"을 추적하고, 규칙 감점은 그 지표로 판정한다. (T-11 후속 floor 조정 라운드는 별개로 가능.)
6. **추천 실패 시 대체 순서를 둔다.** 당근 동네생활처럼 — 우리는 외부 랭킹(`external_ranking`)이 그 자리다.
7. **콘텐츠 임베딩은 버리지 않는다.** 두 회사도 콜드스타트 때문에 결국 도입했다. 로그가 쌓이면 행동 신호를 **더하는** 방향이지 대체가 아니다.
