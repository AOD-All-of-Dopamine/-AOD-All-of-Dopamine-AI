# 부하·메모리 관문 결과 (Task 17, 재실행)

> **이 수치는 개발 PC 기준이다.** Docker Desktop VM 이 이 PC 에서 쓸 수 있는 자원(8 코어 /
> ≈7.5GiB)이 추천 호스트(8GB, 코어 수 다를 수 있음)와 다를 수 있다 — **추천 호스트에서 같은
> 명령으로 다시 잰다.** 동시 5 실패의 남은 원인(steam 지연)은 CPU 경합이 아니라 "계산 스레드가
> 1개뿐" 이라는 설계 자체에서 온다(§ 판정과 권고) — 호스트 코어가 늘어도 근본적으로는 같은 모양의
> 병목이 재현될 가능성이 높다.

## 이 재실행에서 바뀐 것

1. **TMDB 엔진 최적화**(커밋 `634f520`·`c8ec317`, 결과 불변) 반영 — 엔진 이미지 재빌드
   (`dev.sh up` 의 `--build`). in-process 50-seed k=50 871ms → 101ms 개선이 그대로 나타난다(아래
   표: 동시1 p95 최대 197ms, 이전 1100ms).
2. **`rec-webtoon` `cpus: 0.5 → 1.0`**(`compose.yaml`, BLAS 스레드 환경변수는 그대로 1) — 이전
   실행에서 "동시 1 부터 p95 관문 실패, 코퍼스가 가장 작은데도 가장 나쁨" 으로 지목했던 CFS
   스로틀링 가설이 그대로 확인됐다: 코어 1개를 온전히 주니 동시1·5 모두 완전히 통과로 바뀌었다
   (아래 표).

정상 상태로 돌아온 걸 확인하고 계속했다.

## 재실행 방법

```bash
bash recommendation/serving/scripts/dev.sh up
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.e2e   # {"checks": 54, "failed": 0}

# 플랫폼별로 나눠서(이번 실측 방식 — 느린 플랫폼 하나가 오래 걸려도 나머지 결과는 따로 남는다)
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.loadgate --out /tmp/g.json \
  --platforms steam --skip-router > <스크래치>/gate_steam.json 2> <스크래치>/gate_steam.log
# ... tmdb · webtoon · webnovel 도 동일하게
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.loadgate --out /tmp/g.json \
  --platforms steam,tmdb,webnovel --skip-engines > <스크래치>/gate_router.json 2> <스크래치>/gate_router.log

docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}\t{{.CPUPerc}}"
```

측정 방법·`loadgate.py` 의 셀 크기 규칙·상태 코드 분류(`ok`/`busy`/`other_err`/`partial`)는 이전
실행과 동일하다(코드 변경 없음).

## `WORKERS: 2` 시험 (이전 빌드에서 측정 — TMDB 최적화 전 · webtoon cpus 0.5)

이 절은 **재실행하지 않았다** — 아래 수치는 이전 실행(첫 Task 17) 당시 빌드에서 측정한 것이고, 이번
빌드(TMDB 최적화 후)로 다시 재현하지 않았다는 점을 밝혀 둔다. steam 에 대한 결론(개선 없음 — `cpus`
를 그대로 둔 채 프로세스만 늘리면 오히려 tail 지연이 나빠진다)은 이번에도 steam 코드가 바뀌지 않았고
`cpus` 도 그대로라 유효하다고 본다. tmdb·webtoon 은 이제 원인(코드 지연·CFS 스로틀링)이 각각
해소됐으므로 이 표의 결론은 더 이상 적용 대상이 아니다(참고용으로만 남긴다).

| 플랫폼 | 지표 | WORKERS=1(기준) | WORKERS=2(시험) | 채택 |
|---|---|---|---|---|
| steam | 동시5 최악 p95 / busy 합(9칸) | 2212ms / 34 | 2604ms / 17 | 아니오 — p95 악화 |
| tmdb | 동시5 최악 p95 / busy 합(9칸) | 2211ms / 46 | 3359ms / 31 | 아니오 — p95 악화(TMDB 최적화 전 빌드) |
| webtoon | 동시1 최악 p95(참고 — 이미 실패, cpus=0.5 시절) | 1849ms | 1620ms | 동시1도 여전히 실패(cpus 0.5 시절) |
| webtoon | 동시5 최악 p95 / busy 합(9칸) | 3495ms / 66 | 4580ms / 66 | 아니오 — 큰 폭 악화(cpus 0.5 시절) |

시험 후 `WORKERS` 환경변수는 제거하고 원래 설정(WORKERS=1)으로 되돌려 확인했다 —
`compose.local.yaml` 최종 diff 에는 흔적이 남지 않는다.

## 판정 요약 (이번 실행 기준)

| 기준 | 결과 |
|---|---|
| 엔진 p95 ≤ 1,500ms & busy 0 (동시1) | steam ✅ · tmdb ✅ · webtoon ✅ · webnovel ✅ — **4/4 통과** |
| 엔진 p95 ≤ 1,500ms & busy 0 (동시5) | steam ❌(유일한 실패) · tmdb ✅ · webtoon ✅ · webnovel ✅ — **3/4 통과** |
| 라우터 전체 탭 p95 ≤ 1,500ms & partial 0 (동시1) | ✅ (마진 약 118ms, seeds=50 칸) |
| 라우터 전체 탭 p95 ≤ 1,500ms & partial 0 (동시5) | ❌ (steam 동시5 실패가 그대로 전파) |
| 엔진 peak_mb ≤ mem_limit 의 80% | ✅ (4개 전부, 최악 steam 61.2%) |

**종합: DONE_WITH_CONCERNS (이전보다 크게 개선).** TMDB 최적화와 webtoon `cpus` 조정으로 동시1
관문은 4/4 엔진·라우터 모두 통과, 동시5 관문도 tmdb·webtoon·webnovel 3개가 전부 통과로 바뀌었다.
**남은 실패는 steam 하나**(동시5 p95 2970ms, busy 40/135)와 그로 인한 라우터 동시5 뿐이다 — steam
은 이번 태스크에서 코드도 `cpus` 도 건드리지 않았다.

## 판정과 권고

**(a) MVP(소수 사용자) 판정 — 동시1 결과와 단일 요청 지연(seeds 1/10/50) 기준**

동시1(요청을 겹치지 않게 순차로 보낸 것)에서는 4개 엔진과 라우터 전체 탭이 전부 통과한다. 단일 요청
지연(p95, seeds 1→10→50 순):
- steam 474 → 906(637→906 은 오타 아님, seeds10·seen500 이 최악) → 924ms — seeds 가 늘수록 확실히
  느려진다(코퍼스가 가장 크다).
- tmdb 65 → 145 → 208ms, webtoon 155 → 203 → 266ms, webnovel 144 → 211 → 233ms — 셋 다 seeds 수에
  거의 영향받지 않을 만큼 빠르다.
- 라우터 전체 탭(세 엔진 동시 호출, 사실상 최댓값): 469 → 770 → **1382ms**.

**결론: 소수 사용자가 겹치지 않게(직렬에 가깝게) 쓰는 MVP 트래픽이라면 지금 구성으로 통과다.**
다만 seeds=50 라우터 요청은 1,500ms 예산의 92% 를 이미 쓴다 — steam 코퍼스가 가장 큰 쪽에서 오는
근본 여유 부족이라, 사용자가 시드를 많이 채울수록(찜 목록이 큰 사용자) 마진이 줄어든다는 점을
운영 시 염두에 둬야 한다.

**(b) 용량 추정 — 라우터 동시5 수치에서 유도**

동시1(요청이 거의 겹치지 않는 상태)은 깨끗하고, 동시5(5건이 사실상 동시에 몰린 상태)는 15건 중
10~14건이 `partial` 이 된다 — 안정적으로 버티는 지점은 그 사이 어딘가다. 병목은 steam 하나뿐이고
계산 스레드가 1개라 **완전 직렬**이다: 요청 하나 처리에 seeds 수에 따라 대략 0.3~0.9초(p50 기준)가
걸리고, 대기열 마감(`QUEUE_DEADLINE_MS=1500`)을 넘긴 요청은 계산 없이 버려진다. 즉 이 호스트 한
대가 steam 을 거치는 all-tab 트래픽을 큐 적체 없이 꾸준히 소화하려면 산술적으로 **초당 1건 안팎
(1/0.6~0.9초 ≈ 1.1~1.7 req/s, 그것도 순간 몰림 없이 고르게 들어올 때 얘기)**이 안전한 상한이다.
동시에 2~3건 이상이 steam 쪽에 쌓이기 시작하면(예: 사용자 여러 명이 같은 순간 전체 탭을 새로고침)
`partial` 비율이 빠르게 올라간다 — 실측(동시5 에서 이미 67~93%)이 이를 보여준다. **이 숫자는
거칠게 잡은 상한이다(대략적인 목측), 실제 호스트에서 다시 재는 것으로 검증해야 한다.**

**(c) 트래픽이 늘 때 — steam 만 다루면 된다**

steam 만 고치면 되는 상황이라 옵션이 단순해졌다:
1. **엔진 복제**: `rec-steam` 컨테이너를 2개 이상 띄우고 라우터(또는 그 앞단)가 라운드로빈/최소
   대기 큐로 분산한다 — 코드 변경 없이 계산 스레드 개수를 인스턴스 수만큼 늘리는 효과라, 지금
   구조(계산 스레드 1개 고정)와 가장 잘 맞는 확장 방향이다.
2. **`cpus` 와 `WORKERS` 를 함께 올린다** — 이번에 확인했듯 `WORKERS: 2` 단독(=cpus 고정)은
   오히려 역효과였다(프로세스 2개가 같은 CPU 예산을 나눠 쓰며 경합). 반대로 webtoon 사례가
   보여주듯 `cpus` 를 실제로 늘려 스로틀링을 풀어 주는 쪽은 효과가 확실하다. steam 에 대해
   `cpus: 4.0 · WORKERS: 2` 처럼 **코어와 프로세스를 같은 비율로 같이 올리면**(웹워커 하나당
   온전한 코어 2개) 이번에 실패했던 조합(코어는 그대로 두고 프로세스만 늘림)과는 다른 결과가
   나올 가능성이 있다 — 이번 태스크에선 시험하지 않았다(범위 밖, 메모리도 워커당 약 1.2GB 씩 더
   필요해 steam 하나로 예산 상당 부분을 쓴다).
3. 둘 다 코드 최적화(TMDB 처럼 "요청과 무관한 계산을 1회로")가 가능하면 가장 저렴하지만, 이번
   태스크 범위 밖이다.

**(d) 실제 호스트에서 재확인**

이 문서 전체가 개발 PC(8 코어/≈7.5GiB, 이 중 컨테이너에 6.5 코어 배정) 기준이다. steam 의 동시5
실패가 CPU 한도 때문(webtoon 처럼)인지 아니면 코드/코퍼스 자체의 계산량 때문(현재 `cpus: 2.0`,
webtoon 의 이전 0.5 보다 이미 4배 넉넉하다는 점에서 순수 CPU 부족보다는 계산량 자체일 가능성이
높다)인지는 실제 호스트에서 같은 관문을 그대로 재실행해서 확인해야 한다 — "재실행 방법" 절의 명령을
그대로 쓴다.

## 캐벗 (이 PC 기준 — 실제 호스트에서 재확인할 것)

- **엔진은 계산 스레드가 1개뿐이다(설계).** 동시 요청은 반드시 줄을 선다 — 동시 5 가 통과하려면
  요청 하나의 계산 시간이 대략 300ms 를 넘지 않아야 한다(5 × 300ms ≈ 1.5s). tmdb·webtoon·webnovel
  은 이제 단일 요청이 충분히 빨라 동시5 를 통과하지만, **steam 은 코퍼스가 가장 커서 seeds 가
  늘수록 단일 요청 자체가 600~900ms 대라 동시5 줄서기 지연이 여전히 예산을 넘긴다.**
- **webtoon 은 `cpus` 상향 하나로 완전히 해결됐다** — 코드도 코퍼스도 그대로인데 동시1 p95 가
  1849ms→175ms, 동시5 가 3495ms→929ms 로 떨어졌다. 이전 진단(CFS 스로틀링)이 실측으로 확인된
  사례다.
- **동시 20 의 대량 `busy`/503 은 여전히 설계된 동작**(대기열 `MAX_QUEUE=8`,
  `QUEUE_DEADLINE_MS=1500`). 판정에도 넣지 않았다(참고치) — 이번 실행에서도 tmdb·webtoon·webnovel
  이 동시20 에서 busy 비율이 높은 건 정상이다(9건 통과 /40건 중, 즉 의도적으로 나머지를 버린다).
- **라우터 동시5 실패는 라우터 자체 버그가 아니다** — steam 하나가 1,500ms 예산 안에 못 끝내면
  라우터가 그 플랫폼을 `partial` 로 빼고 200 을 돌려주는, 설계된 부분 응답이다.
- steam 측정값 일부(동시1 최악 p95, 라우터 seeds=50 동시1)가 이전 실행보다 살짝 나빠졌는데, steam
  코드·설정을 전혀 바꾸지 않았으므로 측정 잡음(n=12 소표본 + 호스트 스케줄링 변동)으로 본다 — 실제
  호스트 재측정 때 표본을 늘리거나(`--per-cell`) 반복 실행으로 확인하면 좋다.
- `dev.sh` 의 `GIT_SHA` 계산 문제(환경 절)는 이번에도 그대로다 — 범위 밖.
- **다음 단계**: 실제 호스트에 배포해 이 문서의 "재실행 방법"을 그대로 실행한다. steam 의 동시5
  실패가 그대로 재현되면 §판정과 권고 (c) 의 옵션(엔진 복제 또는 `cpus`+`WORKERS` 동반 상향)을
  검토한다 — 둘 다 이번 태스크 범위 밖이라 시도하지 않았다.
