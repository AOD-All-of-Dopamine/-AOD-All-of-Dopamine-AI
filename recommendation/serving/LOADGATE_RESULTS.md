# 부하·메모리 관문 결과 (Task 17)

> **이 수치는 개발 PC 기준이다.** Docker Desktop VM 이 이 PC 에서 쓸 수 있는 자원(8 코어 /
> ≈7.5GiB)이 추천 호스트(8GB, 코어 수 다를 수 있음)와 다를 수 있다 — **추천 호스트에서 같은
> 명령으로 다시 잰다.** 특히 동시 5 에서의 실패는 CPU 경합(`cpus` 한도)이 원인으로 보이므로 호스트의
> 실제 코어 배정에 따라 결과가 달라질 수 있다.

**참고 — 이미지 내부 `GIT_SHA` 라벨:** `/health` 의 `engine_sha`/`router_sha` 가 실제로는 `"dev"` 로
찍힌다. `scripts/dev.sh` 의 `GIT_SHA="$(git -C "$HERE" rev-parse --short HEAD ...)"` 계산이,
스크립트가 도커 볼륨 경로를 안 깨뜨리려고 위에서 잡아 둔 `MSYS_NO_PATHCONV=1` 때문에(네이티브
`git.exe` 가 POSIX 스타일 `-C` 경로를 못 받는다) 조용히 실패해 `dev` 로 폴백한다 — 이번 태스크
범위(`compose.yaml`·`loadgate.py`) 밖의 `dev.sh` 기존 문제라 고치지 않았다. 커밋 추적은 위 표의
`f8d971b`(레포 `git rev-parse --short HEAD`)와 `config_hash`(엔진 설정 해시)로 한다.

## 재실행 방법

```bash
# 5개 서비스 기동(빌드 포함) → healthy 대기 → 1500ms 기본 제한 시간으로 e2e
bash recommendation/serving/scripts/dev.sh up
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.e2e   # {"checks": 54, "failed": 0}

# 전체 행렬 한 번에(엔진 4 + 라우터, 약 15~30분) — 표준출력에 최종 JSON, 표준에러에 진행 로그
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.loadgate --out /tmp/gate.json \
  > <스크래치>/gate.json 2> <스크래치>/gate.log

# 또는 플랫폼별로 나눠서(느린 플랫폼 하나가 오래 걸려도 나머지 결과는 따로 남는다) — 이번 실측은 이 방식으로 했다
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.loadgate --out /tmp/g.json \
  --platforms steam --skip-router > <스크래치>/gate_steam.json 2> <스크래치>/gate_steam.log
# ... tmdb · webtoon · webnovel 도 동일하게
bash recommendation/serving/scripts/dev.sh net python -m aod_serving.tools.loadgate --out /tmp/g.json \
  --platforms steam,tmdb,webnovel --skip-engines > <스크래치>/gate_router.json 2> <스크래치>/gate_router.log

docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}\t{{.CPUPerc}}"
```

`loadgate.py` 는 stdlib + httpx + pandas 만 쓴다(엔진 코드 import 없음). 시드·seen 은 코퍼스
`corpus_index.parquet` 키에서 고정 난수(시드 `20260919`)로 뽑는다. 셀당 요청 수는 동시 수의 배수로
올림, **동시 20 은 최소 40**(그 외 동시는 `--per-cell`, 기본 12). 상태 코드는 `ok`(200) · `busy`
(503 `{"error":"busy"}` — 대기열 마감 초과, 설계된 fast-fail) · `other_err`(그 외)로 나누고, 지연
백분위(p50/p95/max)는 `ok` 요청만으로 계산한다. 라우터 표는 `ok`/`other_err`(503
`engines_unavailable`) 외에 `partial`(200 이지만 `partial` 목록이 비지 않은 응답 수)을 따로 센다.

## 판정 기준 (스펙 §7 — 동시 1·5 만 합격 판정, 동시 20 은 참고)

- 엔진 p95 ≤ 1,500ms, `busy` 0건 (동시 1·5)
- 라우터 전체 탭 p95 ≤ 1,500ms, `partial` 0건 (동시 1·5)
- 엔진 `peak_mb` ≤ `mem_limit` 의 80%

## `WORKERS: 2` 시험 (동시5 p95 실패 엔진 대상 — steam·tmdb·webtoon)

플랫폼별 `environment: WORKERS: 2`(+ 충분한 `mem_limit`)로 그 서비스만 다시 띄우고
(`--platforms <p> --skip-router`) 재측정했다. 결과: **세 플랫폼 모두 개선되지 않았다** — 오히려
p95 최악값이 더 나빠졌다(그 대신 `busy` 건수는 줄었다: 대기열에서 바로 거절되던 요청 일부가 이번엔
완주는 하지만 완주까지 더 오래 걸린다 — `cpus` 한도는 그대로 둔 채 프로세스만 늘리니 두 워커가 같은
CPU 예산을 나눠 쓰며 경합한 것으로 보인다).

| tmdb | 동시5 최악 p95 / busy 합(9칸) | 2211ms / 46 | 3359ms / 31 | 아니오 — p95 악화 |
| webtoon | 동시1 최악 p95(참고 — 이미 실패) | 1849ms | 1620ms | 동시1도 여전히 실패 |
| webtoon | 동시5 최악 p95 / busy 합(9칸) | 3495ms / 66 | 4580ms / 66 | 아니오 — 큰 폭 악화 |

세 플랫폼 모두 시험 종료 후 `WORKERS` 환경변수를 제거하고 원래 설정(WORKERS=1, 기본 `mem_limit`)으로
되돌린 뒤 재기동해 확인했다(`compose.local.yaml` 최종 diff 에는 타임아웃 제거 3줄만 남는다 — 이
시험은 흔적을 남기지 않는다). **지시대로 엔진 코드·`cpus` 는 건드리지 않았다.**

## 판정 요약

| 기준 | 결과 |
|---|---|
| 엔진 p95 ≤ 1,500ms & busy 0 (동시1) | steam ✅ · tmdb ✅ · webtoon ❌(9칸 중 2칸 p95 초과) · webnovel ✅ |
| 엔진 p95 ≤ 1,500ms & busy 0 (동시5) | steam ❌ · tmdb ❌ · webtoon ❌ · webnovel 부분 통과(9칸 중 8칸 통과, 1칸 예외) |
| 라우터 전체 탭 p95 ≤ 1,500ms & partial 0 (동시1) | ✅ |
| 라우터 전체 탭 p95 ≤ 1,500ms & partial 0 (동시5) | ❌ (steam·tmdb 동시5 실패가 그대로 전파) |
| 엔진 peak_mb ≤ mem_limit 의 80% | ✅ (4개 전부, 최악 62.2%) |

**종합: DONE_WITH_CONCERNS.** 메모리 관문은 깨끗이 통과하지만, 동시성(지연) 관문은 동시 5 에서
steam·tmdb·webtoon(그리고 그 결과인 라우터 전체 탭) 이 실패한다. 지시된 유일한 교정 수단
(`WORKERS: 2`)을 세 플랫폼 모두 시험했으나 개선되지 않아(오히려 악화) 채택하지 않았고, 엔진 코드나
`cpus` 는 이 태스크 범위 밖이라 고치지 않았다 — 수치를 그대로 기록하고 보고한다.

네 `mem_limit` 모두 `max(현재값, ceil(peak_mb/0.8) 100MB 올림)` 공식으로도 현재값이 이미 더 크다
(예: steam `ceil(1989.8/0.8)`→2,500m ≤ 3,200m). **낮추는 것도 가능은 하지만**(예: steam →2,500m
로도 80% 기준·300MB 여유 기준을 만족) 이번엔 `WORKERS` 를 채택하지 않아 여유 메모리가 필요 없어
그대로 뒀다 — 합계는 여전히 6,456MB ≤ 6,500MB 예산 안. `cpus` 합은 5.5 / 8 코어(이 PC).
`compose.yaml` 에 서비스별로 실측 근거(peak_mb·비율·판정)를 주석으로 남겼다.

`compose.local.yaml` 은 웹소설 최적화 이전에 걸어 둔 `ENGINE_TIMEOUT_MS: 8000` 임시 오버라이드를
제거했다(기본값 1500ms 로 복귀) — 웹소설이 이제 k=50 에서 ~0.2s 라 8000ms 오버라이드가 더 이상
필요 없고, 실제로 1500ms 로 e2e 가 그대로 통과한다(아래).

## 캐벗 (이 PC 기준 — 실제 호스트에서 재확인할 것)

- **엔진은 계산 스레드가 1개뿐이다(설계, `aod_serving/engine/app.py` 참고 — Arrow/mimalloc
  SIGSEGV 회피).** 동시 요청은 반드시 줄을 선다 — 동시 5 가 통과하려면 요청 하나의 계산 시간이
  대략 300ms 를 넘지 않아야 한다(5 × 300ms ≈ 1.5s). 이 PC 에서는 steam·tmdb·webtoon 의 단일 요청
  계산 시간 자체가 이미 그 근처거나 넘는다(동시1 p95 로도 steam 최대 813ms, tmdb 1100ms, webtoon
  최대 1849ms) — 그래서 동시 5 부터 줄서기 지연이 관문을 넘긴다.
- **webtoon 이 코퍼스가 가장 작은데도(3,687행) 4개 중 가장 나쁘다.** `cpus: 0.5` 의 CFS 스로틀링
  (100ms 주기당 50ms 쿼터)으로 보인다 — 동시 1 에서도 p95 가 튄다(1,782ms·1,849ms). `WORKERS: 2`
  는 같은 0.5 코어를 두 프로세스가 나눠 쓰게 만들어 오히려 더 나빠졌다(최대 p95 4,580ms). 코드
  최적화나 `cpus` 조정은 이 태스크 범위 밖이라 시도하지 않았다 — 실제 호스트에서 코어가 더 넉넉하면
  결과가 달라질 수 있다.
- **동시 20 의 대량 `busy`/503 은 설계된 동작이다**(대기열 `MAX_QUEUE=8`, `QUEUE_DEADLINE_MS=1500`
  — 마감을 넘긴 대기 요청은 계산하지 않고 바로 503 `busy`). 판정에도 넣지 않았다(참고치).
- **라우터 동시5 실패는 라우터 자체 버그가 아니다** — steam·tmdb 엔진이 1,500ms 예산 안에 못
  끝내면 라우터가 그 플랫폼을 `partial` 로 빼고 200 을 돌려주는, 설계된 부분 응답이다(스펙 §8-5).
  엔진이 고쳐지면 라우터 표도 같이 좋아진다.
- **`WORKERS: 2` 시험은 세 플랫폼 모두 역효과였다** — `busy`(즉시 거절) 건수는 줄지만 완주하는
  요청의 tail 지연이 늘어 p95 는 오히려 나빠졌다. `cpus` 를 그대로 둔 채 프로세스만 늘리는 방식의
  한계로 보인다.
- **`dev.sh` 의 `GIT_SHA` 계산이 `MSYS_NO_PATHCONV=1` 때문에 실패해 이미지 내부 라벨이 `dev` 로
  찍힌다**(환경 절 참고) — 이번 태스크 범위 밖이라 고치지 않았다.
- 이 PC 의 Docker VM 은 8 코어 / ≈7.5GiB, 컨테이너 `cpus` 합은 5.5(호스트 OS·다른 프로세스 몫으로
  2.5 코어 남김) — 실제 추천 호스트의 코어 수·다른 워크로드 유무에 따라 동시5 결과가 달라질 수
  있다. **다음 단계: 실제 호스트에 이미지를 배포하고 `LOADGATE_RESULTS.md` 의 "재실행 방법"을 그대로
  실행해 동시5 관문이 통과하는지 확인한다.** 여전히 실패하면 그때 `cpus` 상향이나 엔진 쪽 최적화를
  검토한다(둘 다 이번 태스크 범위 밖).
