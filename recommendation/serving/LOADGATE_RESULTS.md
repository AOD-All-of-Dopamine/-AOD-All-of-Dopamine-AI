# 부하·메모리 관문 결과 (Task 17, 최종 실행)

> **이 수치는 개발 PC 기준이다.** Docker Desktop VM 이 이 PC 에서 쓸 수 있는 자원(8 코어 /
> ≈7.5GiB)이 추천 호스트(8GB, 코어 수 다를 수 있음)와 다를 수 있다 — **추천 호스트에서 같은
> 명령으로 다시 잰다.** 동시 5 의 남은 실패(steam)는 CPU 경합이 아니라 "계산 스레드가 1개뿐"
> 이라는 설계 자체에서 온다(§ 판정과 권고) — 호스트 코어가 늘어도 근본적으로는 같은 모양의
> 병목이 재현될 가능성이 높다.

## 이번 실행에서 바뀐 것

1. **Steam 2차 최적화**(커밋 `e767fe4`, 결과 불변) — in-process k=50: 3 시드 321→194ms, 50 시드
   684→397ms. 엔진 이미지 재빌드(`dev.sh up` 의 `--build`).
2. **라우터 입력 한도 검증**(`a7c4c82`) — 잘못된 입력을 라우터에서 422 로 직접 검증(예외는 JSON
   500). 정상 입력의 지연에는 영향이 없다(검증만 추가됐다) — 측정에서도 그렇게 나온다.
3. **"서빙 가능 목록"(catalog allowlist) 기능 추가**(`bd7607a`·`b879942`) — 엔진이 `CATALOG_KEYS_URL`
   로 백엔드에서 키 목록을 받아 후보를 그 목록으로 제한할 수 있다. `compose.local.yaml` 이 이제
   `http://host.docker.internal:8080/api/recommendations/catalog-keys?platform=…` 를 가리키는데,
   **그 백엔드 엔드포인트는 아직 없다** — 엔진은 뜨고 경고 로그 한 줄만 남긴 뒤 **필터 없이(전체
   코퍼스) 서빙**한다(`/health.catalog.last_error` 로 확인). **이 문서의 메인 측정(엔진별 표·라우터
   표)은 전부 이 상태(필터 없음 — 최악 케이스, 전체 코퍼스) 에서 쟀다.** 목록을 실제로 켰을 때의
   효과는 별도 절(§ 서빙 가능 목록 켠 상태)에서 steam 하나로만 따로 쟀다.

## 서빙 가능 목록 켠 상태 (Steam, 896키)

**방법.** Steam `corpus_index.parquet` 의 `steam_appid` 를 오름차순 정렬 후 **194개마다 하나씩**
(`keys[::194]`, 0 부터 시작) 뽑아 파일로 저장했다 — 173,691행 기준 **896개**가 나온다(지시받은
"894개" 와 2개 차이인데, `173691/194 ≈ 895.3` 이라 슬라이싱 시작점에 따라 895~896 사이로 갈린다 —
894 는 근사치였던 것으로 보이고, 여기서는 재현 가능한 정확한 방법(오름차순 정렬 · 194 간격 ·
인덱스 0 부터)을 그대로 적었다). 이 파일을 레포 밖(세션 스크래치 디렉터리)에 두고, **커밋하지 않는**
임시 compose 오버레이 파일 하나로 `rec-steam` 만 `CATALOG_KEYS_URL` 을 비우고
`CATALOG_KEYS_FILE` 로 이 파일을 가리키게 했다(`docker compose -f compose.yaml -f
compose.local.yaml -f <스크래치>/compose.catalog.yaml up -d --build rec-steam`). `/health.catalog`
로 확인:

```
{'enabled': True, 'size': 896, 'matched': 896, 'source': 'file', 'last_error': None}
```

896개 전부 코퍼스에 있는 키라 `matched` 도 896 — 예상대로(카탈로그 파일 자체를 코퍼스에서 뽑았다).

별개로 남아 있어 무거운 요청의 tail 지연은 완전히 없어지지 않는다.

**요청당 반환 개수(`k=50`) — "훨씬 적게 돌아온다" 는 예상과 다르게, 시드 수에 따라 갈렸다.**
896개 카탈로그(코퍼스의 0.5%)에서 무작위 고정 시드(20260919)로 뽑은 대표 샘플:

1개 시드로 8건 더 시도(다른 난수 시드)해 보니 8~50개 사이에서 크게 흔들린다(`[47, 50, 31, 50, 49,
37, 27, 34]`) — **그 시드 하나가 카탈로그 안에서 이웃이 얼마나 있는지**에 따라 갈린다는 뜻이다.
시드가 10개·50개로 늘면 여러 시드의 이웃을 합쳐서 웬만하면 50개를 채운다(`exhausted=False`) —
"후보 50개 중 카드로 만들 수 있는 게 0~1개" 라는 최악 시나리오(카탈로그가 코퍼스의 0.2% 수준일 때)
는 이번 896키(0.5%) 규모에서는 시드가 1개일 때만, 그것도 그 시드에 따라 나타난다.

메모리: `peak_mb` 1960.1 (mem_limit 3200m 의 **61.3%**, 미필터 상태와 비슷하다 — 카탈로그 필터
자체는 메모리를 더 먹지 않는다). 측정 후 `rec-steam` 을 원래 설정(`CATALOG_KEYS_URL`, 파일 마운트
없음)으로 되돌리고 `/health.catalog` 가 다시 미필터 상태(`source: url`, 이전과 같은 `last_error`)
로 돌아온 것을 확인했다.

하나 · 그중에서도 seeds=50(무거운 요청) 뿐**이다.

## 판정과 권고

**(a) MVP(소수 사용자) 판정**

동시1 은 4개 엔진·라우터 세 시드 수 전부 통과, 마진도 넉넉하다(라우터 최악 591ms, 1,500ms 예산의
39% 만 쓴다 — 직전 실행 1382ms/92% 대비 크게 좋아졌다). **소수 사용자가 겹치지 않게 쓰는 MVP
트래픽은 지금 구성으로 여유 있게 통과다.** seeds=50 요청(찜 목록이 큰 사용자)도 동시1 이라면
문제없다(591ms).

**(b) 용량 추정 — 라우터 동시5 수치에서 유도**

이번 실행에서는 seeds 1·10 이 동시5 에서 **완전히 깨끗하다**(partial 0, p95 857·1202ms) — 즉
"보통 시드 수(1~10개)" 트래픽이라면 **동시 5건이 몰려도 문제없다**. 병목은 seeds=50 같은 무거운
요청이 steam 계산 스레드를 오래 붙잡을 때만 나타난다: steam 단일 요청(seeds=50, 동시1) 이 이미
420~494ms, 동시5 에서 그 5배 가까이 줄서기가 쌓이면 1,500ms 예산을 넘긴다(대기열
`QUEUE_DEADLINE_MS=1500` 설계상 그 이상은 `partial`). 산술적으로: 무거운(50시드) all-tab 요청은
초당 **1.5~2건 안팎**(1/0.42~0.49초)까지는 괜찮고, 그 이상 몰리면 partial 이 나타나기 시작한다 —
직전 실행(초당 1건 안팎)보다 상한이 올라갔다. 가벼운 요청(1~10시드)은 이번 실행 기준 동시5 까지
문제가 없었으니 상한을 더 높게 잡아도 된다. **이 숫자들은 거칠게 잡은 상한이다 — 실제 호스트에서
다시 재는 것으로 검증해야 한다.**

**(c) 트래픽이 늘 때**

steam 의 남은 문제가 좁혀졌다(이제 "무거운 요청(seeds 多)의 동시5" 뿐):
1. **서빙 가능 목록을 실제로 켠다** — 이번 보조 측정에서 후보 풀이 173,691→896개로 줄자 동시5
   `busy` 가 9/135→0/45 로 **완전히 사라졌다**(대기열 마감을 넘기는 일 자체가 없어졌다). 다만
   seeds=50 무거운 요청의 p95 는 여전히 1,500ms 를 살짝 넘는다(1722ms) — 시드 수에 비례하는
   계산량은 후보 풀 크기와 별개라서다. 백엔드 카탈로그 엔드포인트가 실제로 준비되면(이 기능은 이미
   구현·배포 가능한 상태다) 이 정도 개선은 코드 변경 없이 공짜로 따라온다.
2. **엔진 복제**(steam 만 2개 이상) 또는 **`cpus`·`WORKERS` 동반 상향** — 직전 문서와 같은 결론:
   `WORKERS` 단독(고정 `cpus`)은 역효과였다(경합). 코어와 프로세스를 같은 비율로 올리는 조합은
   이번에도 시도하지 않았다(범위 밖).
3. seeds=50 자체의 계산 경로를 더 최적화하는 것(이미 두 차례 최적화됐다)도 유효한 방향이지만
   범위 밖이다.

**(d) 실제 호스트에서 재확인**

이 문서 전체가 개발 PC 기준이다. **카탈로그 기능은 이번 실행 내내 "백엔드 없음 → 필터 없이 서빙"
상태였다** — 실제 호스트에서 백엔드 카탈로그 엔드포인트가 준비되면(§서빙 가능 목록 절이 그 효과의
근사치를 보여준다) steam 의 남은 동시5 실패가 상당 부분 저절로 좋아질 가능성이 높다. "재실행 방법"
절의 명령을 그대로 실제 호스트에서 돌려 확인한다.

## 캐벗 (이 PC 기준 — 실제 호스트에서 재확인할 것)

- **엔진은 계산 스레드가 1개뿐이다(설계).** steam 이 두 차례 최적화됐어도 seeds=50 같은 무거운
  요청은 단일 요청 자체가 400~500ms 대라 동시5 줄서기가 여전히 예산에 걸린다. tmdb·webtoon·webnovel
  은 이제 충분히 빨라 세 플랫폼 다 동시5 를 완전히 통과한다.
- **서빙 가능 목록(카탈로그)을 켜면 동시5 의 `busy`(대기열 마감 초과)가 사라진다** — 후보 풀이
  줄면 계산 자체가 빨라지기 때문이다. 다만 "시드 수에 비례하는" 부분(이웃 탐색을 시드마다 한다)은
  후보 풀 크기와 무관하게 남아, 무거운 요청(50시드)의 p95 는 여전히 근소하게 예산을 넘겼다.
- **카탈로그가 켜졌을 때 `k=50` 요청이 몇 개를 돌려주는지는 시드 수와 그 시드의 카탈로그 내 이웃
  밀도에 크게 좌우된다** — 시드 1개면 8~50개로 크게 흔들리고(그 시드 근처에 카탈로그 항목이
  얼마나 있느냐에 달렸다), 시드 10·50개면 여러 시드의 이웃을 합쳐 대개 50개를 채운다. "카드로 만들
  수 있는 게 0~1개" 라는 최악 시나리오(모듈 머리말)는 카탈로그가 지금(896키, 코퍼스의 0.5%)보다
  훨씬 작을 때(0.2% 수준) 더 뚜렷해질 것으로 보인다 — 실제 백엔드 카탈로그 크기로 다시 재는 게
  좋다.
- **동시 20 의 대량 `busy`/503 은 여전히 설계된 동작**(대기열 `MAX_QUEUE=8`,
  `QUEUE_DEADLINE_MS=1500`). 판정에도 넣지 않았다(참고치).
- **라우터 동시5 의 남은 실패는 라우터 자체 버그가 아니다** — steam 의 seeds=50 케이스가
  1,500ms 예산 안에 못 끝나면 라우터가 그 플랫폼을 `partial` 로 빼고 200 을 돌려주는, 설계된 부분
  응답이다.
- 라우터 입력 한도 검증(`a7c4c82`) 은 정상 입력의 지연에 영향이 없다 — 이번 실행에서도 그렇게
  나왔다(검증 실패 경로만 새로 422 를 돌려준다).
- `dev.sh` 의 `GIT_SHA` 라벨 문제는 이번에도 그대로다 — 범위 밖.
- **다음 단계**: (1) 실제 호스트에서 같은 관문을 재실행, (2) 백엔드 카탈로그 엔드포인트가 준비되면
  실제 카탈로그 크기로 다시 재서 §서빙 가능 목록 절의 근사치를 검증, (3) 그래도 steam seeds=50
  동시5 가 실패하면 §판정과 권고 (c) 의 옵션(엔진 복제 또는 `cpus`+`WORKERS` 동반 상향)을 검토한다
  — 셋 다 이번 태스크 범위 밖이라 시도하지 않았다.
